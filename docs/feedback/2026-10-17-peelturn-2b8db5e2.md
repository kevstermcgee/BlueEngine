## Generated mechanic

Launch a packet of beads across a grid. Whenever it hits an obstacle, it leaves one bead behind as a permanent obstacle, turns clockwise, and continues with the remaining beads. Each launch builds the maze that redirects its own later movement.

## Novelty and playtesting

The closest comparison is Ricochet Robots, whose pieces slide until obstacles stop them. [Publisher description](https://www.riograndegames.com/games/ricochet-robots/). Peelturn replaces separately chosen movements with a finite automatic route: every collision consumes a bead, creates a permanent stopper, and forces a clockwise continuation. Unlike the prior Impact Orchard, deposited pieces never release stored attacks or activate each other; they change collision geometry. No supplied prior mechanic uses this rule. This comparison cannot certify worldwide originality or fun.

Long routes could become tedious mental simulation, while generous previews could reduce play to trying every direction. Begin with short packets, preview only the first impact, animate subsequent impacts clearly, and test whether players can explain their launch choices rather than guessing.

### 1. tooling (low)

Observed: Start marks the supplied game folder blocked because protected metadata directories make it nonempty.

Reproduce: Run new-game start with a precreated destination containing protected metadata directories.

Workaround: Scaffolded into a child directory, moved generated files into the game root, and corrected relative engine paths.

Proposed engine improvement: Support scaffolding into metadata-only directories while refusing content-file collisions.

### 2. workflow (medium)

Observed: The changed-file planner classifies the new standalone game as unknown and selects the full engine suite despite no engine edits.

Reproduce: Add a standalone game under games/ and run be2.py check --changed --plan.

Workaround: Used explicit check --game inner, integration and shipping gates.

Proposed engine improvement: Recognize standalone game boundaries and route their changes to game checks.

### 3. platform (medium)

Observed: Native capture fails with XOpenDisplay() failed. This sandbox forbids Xvfb display-socket binding, and shipping skips smoke without a display.

Reproduce: Run tools/xcapture.py against the compiled game in this restricted environment without DISPLAY.

Workaround: Verified compilation and package integrity; documented pending visual, control and device checks in VERIFICATION.md.

Proposed engine improvement: Preflight display connectivity and report retained Xvfb diagnostics as an environment blocker before launching the client.

### 4. tooling (medium)

Observed: xcapture reports XOpenDisplay() failed without exposing the underlying Xvfb socket failure. A direct socket probe confirmed Operation not permitted.

Reproduce: Run tools/xcapture.py against the native game in a sandbox that denies AF_UNIX socket binding.

Workaround: Ran rule, integration, lint, and package checks; documented pending native visual and control inspection in VERIFICATION.md.

Proposed engine improvement: Retain Xvfb stderr and report display startup failures before launching the game.

### 5. audio (medium)

Observed: The isolated Linux smoke log contains an audio-worker panic, 'Can't set rate.', although rendering completed and the smoke receipt passed. Audible cues are therefore unverified.

Reproduce: Run isolated native smoke on an ALSA host that rejects the requested sample rate; inspect stderr alongside the successful screenshot result.

Workaround: Use --mute for visual verification; check audible cues separately on supported audio hardware.

Proposed engine improvement: Handle audio-device negotiation failure gracefully and report degraded audio separately from visual smoke success.
