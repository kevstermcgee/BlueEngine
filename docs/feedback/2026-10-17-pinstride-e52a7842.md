## Generated mechanic

Move a rigid baton through a three-dimensional obstacle chamber by swinging it 90 degrees around its pinned tip. After every swing, the arriving tip automatically becomes the new pin and the old pin releases. Every move therefore changes both your position and the pivot available for your next move.

## Novelty and playtesting

The closest comparison is Bloxorz's rigid-object route planning toward a goal. [Bloxorz instructions](https://www.coolmathgames.com/0-bloxorz). Pinstride replaces floor-supported rolling with alternating endpoint pivots through a fully spatial volume, making the swept arc and next anchor central. Among the supplied mechanics, Rotation Relay also uses rotation, but transfers angular velocity to rotate an arena; Pinstride moves only the baton and automatically hands its anchor between tips. This comparison cannot certify worldwide originality or fun.

The automatic anchor handoff may feel restrictive, and occlusion may turn spatial planning into camera wrestling. Test whether players can identify the next pinned tip and explain a blocked swing after the tutorial. Use open chamber framing, distinctive tip shapes, and an unmistakable anchor pulse; expand beyond three rooms only if deliberate two-swing plans emerge.

### 1. tooling (low)

Observed: The start command rejected the game destination as nonempty when it contained only reserved workspace directories.

Reproduce: Run be2.py start with a new-game project directory containing only .git, .agents, .codex and .aws workspace mounts.

Workaround: Generated the canonical scaffold in a child directory, moved its files into the game folder, and corrected the relative engine paths.

Proposed engine improvement: Allow scaffolding into reserved-directory-only workspaces while preserving those directories.

### 2. audio (medium)

Observed: Native captures started an ALSA worker that panicked with 'Can't set rate' despite --mute. Rendering continued.

Reproduce: On this Linux host, launch Pinstride under Xvfb with --mute --capture NEW_DIR --frames 20 without an ALSA null configuration.

Workaround: Used a temporary ALSA null-output configuration for software captures and package smoke. Physical audio remains unverified.

Proposed engine improvement: Avoid opening audio devices during silent runs, handle backend initialization errors without panicking, and add a muted no-device smoke test.

### 3. audio (medium)

Observed: Engine dependency friction: the muted isolated-package smoke log contains a nonfatal ALSA worker panic during sample-rate setup. Rendering and gameplay continued.

Reproduce: Run the packaged native capture on a Linux software-rendering host whose default ALSA device rejects the requested rate.

Workaround: The project documents using an ALSA null output for muted automation. Verify audible output separately on supported hardware.

Proposed engine improvement: Provide device-free muted startup or graceful audio-device failure handling in the native runtime.

### 4. tooling (medium)

Observed: The shared smoke gate recorded success despite the audio worker panic. It checks process exit and nonblank captures, so its success cannot establish subsystem health.

Reproduce: Allow a background audio worker to panic while the main process still produces captures and exits successfully.

Workaround: Inspect smoke stderr alongside captures and keep visual smoke evidence separate from audio verification.

Proposed engine improvement: Surface worker failures explicitly in smoke results, distinguishing successful rendering from degraded audio.
